### Session 1 — Establishing the deterministic-core boundary (prompt layer)

**Stage:** Requirements classification → architecture boundary → plan approval.

**Agent prompt I issued (paraphrase):**
> We are building an insurance claim adjudication pipeline with five agents. The LLM must
> only read free text and write narrative explanations. Every numeric score, every boolean
> eligibility decision, and every threshold check must be computed by plain Python code.
> Produce a system prompt for each agent that states this boundary explicitly, and show me
> the plan before writing any code.

**Agent's first plan:** a single prompt asking the model to "analyse the claim and decide
whether it is fraudulent / eligible", letting the LLM return the final decision.

**My intervention — REJECTED, redirected.**
*Rationale:* leaving the approve/reject call to the LLM makes the result non-deterministic
and unauditable; a regulator could not reproduce why a claim was flagged. The assignment
requires at least one safety-relevant boundary where deterministic code constrains the AI
output. I required the prompts to split each agent into a **deterministic core** (code) and a
**narrative layer** (LLM).

**Approved plan:**
- `eligibility_agent.py`: five boolean checks in code (policy active, within coverage period,
  waiting period satisfied, claim type covered, amount within max coverage); LLM only
  translates the outcome into underwriting language.
- `fraud_detection_agent.py`: numeric score from four heuristics in code; LLM only surfaces
  narrative red flags from the incident description.
- `document_verification_agent.py`: completeness check in code against
  `business_rules.required_documents_for(claim_type)`; LLM only assesses content quality.
- `claim_summary_agent.py`: pure LLM narrative synthesis.
- `human_approval_agent.py`: deterministic escalation triggers; no LLM decision.

**Evidence in the final code:**
- `agents/eligibility_agent.py` lines 42–65: booleans computed from policy dates/amounts;
  `is_eligible = len(reasons) == 0`.
- `agents/fraud_detection_agent.py` lines 48–85: heuristic score computed in code;
  line 116 the LLM can only *add* to the score (`score + 5 * len(patterns)`), never lower it.
- `prompts/eligibility_prompt.py`, `prompts/fraud_detection_prompt.py`,
  `prompts/document_verification_prompt.py`: each system prompt states the LLM does not make
  the completeness/eligibility/fraud determination.

**Verification gate I applied:** I asked the agent to quote, in each prompt, the exact
deterministic responsibility the LLM must not touch, and checked that no prompt asks the
model to return a boolean or a capped amount.

### Session 2 — Building the offline test harness and the five mandated scenarios

**Stage:** Plan approval → build → verification compliance.

**Agent prompt I issued (paraphrase):**
> Build a pytest suite that runs the full `ClaimService` facade (the same path the Streamlit
> UI uses) for the five mandated scenarios: approve, missing-documents reject, expired-policy
> reject, high-fraud human review, high-value human review. The suite must run offline with no
> API key. Show the fixture design before writing tests.

**Agent's first draft:** tests called the real Gemini client directly, so the suite failed
whenever no key was configured.

**My intervention — REJECTED the live dependency in tests, redirected to a stub.**
*Rationale:* verification must be deterministic and repeatable; tests cannot depend on API
availability, token cost, or model non-determinism. I required a fake LLM service that always
raises `LLMServiceError`, forcing every agent through its documented deterministic fallback
path while still exercising the full code path.

**Approved implementation (evidence in repo):**
- `tests/conftest.py`: `StubLLMService` raises on both `generate_text` and
  `generate_structured`; `MAX_RETRIES=0` so guaranteed-failing calls pay no backoff latency.
  The `make_claim_input` factory builds a valid `ClaimInput` with tunable amount, coverage,
  policy dates, prior claims, and document set.
- `tests/test_scenarios/test_five_mandated_scenarios.py`: five acceptance tests through
  `ClaimService.run_claim`, plus `resume_claim` for the two human-review scenarios.

| # | Scenario | Input (factory parameters) | Expected outcome |
|---|---|---|---|
| 1 | Complete valid claim | 45,000 / 1,000,000; policy 900 days old; docs present | `APPROVED`, not paused |
| 2 | Missing documents | `include_documents=False` | `REJECTED`, reason mentions missing/document |
| 3 | Expired policy | policy ended 60 days ago; docs present | `REJECTED` |
| 4 | Suspicious claim | 700,000 / 1,000,000; policy 3 days old; 6 prior claims | paused → human review; resume → `HUMAN_APPROVED` |
| 5 | High-value claim | 1,900,000 / 2,000,000; policy 900 days old | paused → human review; resume → `HUMAN_APPROVED` |

**Additional unit tests I directed:**
- Required-document rules per claim type (`core/config/business_rules.py`): health 4 docs,
  motor 5 docs, etc.
- Fraud tier boundary: HIGH ≥ 70, MEDIUM ≥ 40, else LOW (`settings.fraud_high_risk_score`,
  `fraud_medium_risk_score`).
- Workflow observability: execution log populated after a run.

**Verification gate:** every new test references the scenario or rule it verifies; I ran the
full suite and required zero offline failures before accepting the build.

### Session 3 — Debugging the high-fraud scenario (date alignment)

**Stage:** Verification compliance → architecture revision driven by test evidence.

**Symptom:** scenario 4 (suspicious claim) failed — the claim was rejected by eligibility
before the fraud check ever ran, so the fraud HIGH tier was never exercised.

**Agent's first diagnosis:** it proposed loosening the fraud thresholds to force a HIGH score.

**My intervention — REJECTED that fix, redirected to root cause.**
*Rationale:* lowering thresholds to make a test pass would weaken the safety rule and hide the
real defect. I inspected the fixture and found the incident date fell outside the policy
coverage period, so eligibility correctly rejected it first. The defect was **test-data
alignment**, not the rule.

**Fix I approved:** align the incident date inside the policy period and tune the claim
parameters to reach HIGH legitimately — fresh policy (< 30 days), high coverage ratio,
frequent claimant (≥ 3 prior claims). Evidence: scenario 4 in
`test_five_mandated_scenarios.py` uses policy age 3 days, 6 prior claims, 700,000 / 1,000,000.

**Lesson recorded:** the decision engine runs document completeness and eligibility as hard
gates before any escalation check; a fraud scenario can only be evaluated if the claim first
passes those gates. This ordering is itself an invariant worth a negative test.

### Session 4 — Debugging the fraud scoring unit test (fresh-policy bonus)

**Stage:** Verification compliance.

**Symptom:** the fraud unit test reached only MEDIUM (score 55) instead of HIGH.

**Root cause I identified with the agent:** the test policy was 35 days old, above the
30-day fresh-policy threshold (`MIN_POLICY_AGE_DAYS_LOW_RISK = 30`), so the +25 fresh-policy
bonus was not applied.

**Fix approved:** set the policy start to 16 days before today so the fresh-policy bonus
applies; combined with the round-amount and frequent-claimant heuristics the score reaches the
HIGH tier. I kept the heuristic thresholds in `business_rules.py` unchanged.

**Guard I added:** a boundary check around the fresh-policy threshold (29 days vs 31 days) so
the rule is tested at its edge, not only in the middle.

### Session 5 — Offline graceful degradation and the zero-division guard

**Stage:** Build → verification compliance → robustness.

**Issue raised in review:** if the LLM call fails (missing key, rate limit, malformed JSON
after retries), the workflow must not crash.

**Approved design:** `agents/base_agent.py._safe_llm_narrative()` catches
`LLMServiceError`, logs a warning, and validates a deterministic templated fallback instead
of propagating the failure. Every agent supplies its own fallback narrative. This is the
graceful-degradation invariant: the system still produces a rule-based decision without a
working LLM.

**Additional defect caught in review:** `coverage_fraction` divided by `max_coverage_amount`;
a zero coverage would raise `ZeroDivisionError`. I required a guard so a degenerate policy
returns a safe fraction rather than crashing the run.

### Session 6 — Parallelism and single-file integration

**Stage:** Architecture candidate evaluation → build.

**Context:** the full multi-file build uses LangGraph `StateGraph` with three parallel
branches (document verification, eligibility, fraud) fanning out from one predecessor and
merging at one barrier. For the Phase 1 single-file deliverable the LangGraph dependency was
not allowed.

**Agent's first candidate:** sequential execution of the three checks.

**My intervention — REJECTED, redirected to preserve parallel semantics.**
*Rationale:* sequential order would change the observable workflow and hide the fan-out
design. I approved a `ThreadPoolExecutor` with three workers for the single-file build, with
each thread writing to a distinct key in the shared result dictionary to avoid a race. The
multi-file build keeps the true LangGraph parallel fan-out (`langgraph_workflow/`).

**Integration decisions I approved:**
- dataclass models in the single-file build (standard library, no Pydantic dependency) so the
  file runs anywhere with Python 3; the multi-file build keeps Pydantic v2 schemas.
- Consolidation order: enums → models → business rules → LLM service → five agents → workflow
  → demo scenarios → tests.
- Demo scenarios added for walkthrough testing: approve, missing-docs, expired-policy,
  high-fraud, high-value (mirrored in `assets/demo_claims/` and `demo_upload_pack/`).

## 6. Personal reflection

The main thing I took away is how much cleaner an agent-built system becomes when the
deterministic logic and the LLM calls are separated up front. My first instinct in the early
sessions was to let the model "judge" a claim, but that produces output you cannot test or
defend in an audit. Keeping scores and booleans in plain Python and reserving the LLM for
narrative made every test deterministic and every decision traceable — which is exactly the
safety boundary the project asks for.

Writing the five acceptance scenarios also changed how I debug: a failing test was not
always a code bug. Twice the real problem was misaligned test data (an incident outside the
policy period, a policy too old to qualify as fresh), and the right fix was to correct the
fixture rather than relax the rule. I also learned to look for boundary cases — thresholds
like the 30-day fresh-policy window — because that is where heuristics actually break.

On the human-supervision side, my role was mostly to stop the agent from taking the easy
way out: loosening thresholds, calling the live API in tests, or dropping parallelism for a
simpler sequential version. Each of those would have looked like progress in the moment but
would have weakened the system's auditability or testability. Having the agent show a plan
before code, and rejecting plans that crossed the deterministic/LLM boundary, kept the build
on track.
